# Производительность (CPU-bound): наши последовательности vs `-Oz`

Строгая проверка скорости с **изоляцией вычислений от I/O**: входные данные
читаются **один раз**, дальше многократно прогоняется только вычислительное ядро.
Сравниваются наша лучшая последовательность (минимизирует `.text`) и `opt -Oz` на
**одном и том же** модуле.

## Методика
- LLVM 18.1.3 (`clang`/`opt`/`llc`), линковка `clang -no-pie ... -lm`, codegen по
  умолчанию; исходники — оригинальный cBench V1.1.
- Время `wall-clock`, 5 прогонов; метрика `ours/-Oz` (`≈1.0` = скорость не отличается).
- Как обеспечена изоляция от I/O для каждого бенчмарка:
  - **bzip2** — один проход большого входа (~122 МБ): одно чтение, далее ~21 c
    компрессии (компьют доминирует, I/O ≈ 0.3%).
  - **stringsearch** — программа читает текст и шаблоны **один раз**, затем
    выполняет внутренний цикл `strsearch` (15M поисков по данным в памяти).
  - **sha** — отдельный драйвер: файл читается один раз в буфер, затем цикл ядра
    `sha_init/sha_update/sha_final` без файлового I/O; обёртка-драйвер собрана
    фиксированно `-O2`, так что между вариантами отличается только оптимизация
    ядра `sha.c`.

## bzip2 — 1 проход, ~122 МБ (≈21 c)

| Тест | Наша цепочка, с | -Oz, с |
|---|--:|--:|
| 1 | 21.419 | 21.362 |
| 2 | 21.466 | 21.395 |
| 3 | 21.571 | 21.386 |
| 4 | 21.652 | 21.407 |
| 5 | 21.601 | 21.367 |
| **среднее** | **21.542** | **21.383** |

`ours/-Oz = 1.007×`.

## Сводка

| benchmark | изоляция I/O | время (~) | ours/-Oz | `.text` vs -Oz |
|---|---|--:|--:|--:|
| bzip2 | 1 чтение 122 МБ | 21 c | 1.007× | 24.0% |
| stringsearch | чтение раз + внутренний цикл | 19 c | 1.005× | 7.2% |
| sha | драйвер: чтение раз + цикл ядра | 15 c | 1.001× | 16.5% |

(Выигрыш `.text` — из основного прогона на compiler_gym-модулях, см.
`heuristics_comparison.md`.)

## Вывод

При изоляции вычислений от I/O наши размер-ориентированные последовательности по
**чистому вычислительному времени неотличимы от `-Oz` (≤1%)**. Сокращение размера
кода достигается **без потери производительности**.

## Ограничения
- `wall-clock`-замер чувствителен к состоянию системы (единичные «холодные»
  выбросы; ориентир — среднее и минимум).
- jpeg/tiff/lame/ghostscript не собрались простым `clang` из оригинального cBench
  и в замер не вошли.
- LLVM 18.1.3; на других версиях абсолютные числа могут отличаться.
