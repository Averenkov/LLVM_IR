# Задание для AI-агента (Codex): исправление эвристики cycle_breaking_superpath_topk

## 1. Контекст

Коммит `db33b79` («feat: add TU-aware cycle superpath top-k evaluator») добавил в `src/llvm_ir/stages/translation_unit/evaluate_topk_paths.py` эвристику `cycle_breaking_superpath_topk`: сегменты длины 4–6 генерируются cycle-breaking-ом, **реально измеряются на whole-TU** через prefix cache, затем склеиваются в «суперпути» и top-k склеек оценивается заново. Идея верная, но код-ревью с воспроизведением выявило четыре проблемы. Их нужно исправить, сохранив интерфейс CLI и совместимость формата отчёта.

Воспроизведённые факты (синтетика: сегменты длины 4, плотная склейка — реалистично для delta-графов при `min_edge_weight=1`):

```
_build_superpath_candidates, 60 сегментов:   ~5 c,  0.13 GB
_build_superpath_candidates, 100 сегментов:  ~25 c, 0.62 GB   (дефолт top_starts=10 × paths_per_start=10)
_build_superpath_candidates, 250 сегментов:  процесс убит по OOM (exit 137)
```

Общие правила: на каждый пункт — регрессионный тест, падающий до фикса; существующие 85 тестов остаются зелёными (кроме одного теста, который явно предписано переписать в P2); ключи отчёта не удалять и не переименовывать — только добавлять; стиль кода как в репозитории, без новых зависимостей.

---

## 2. P1 — ограничить перебор в `_build_superpath_candidates` (блокер)

Сейчас DFS перечисляет ВСЕ цепочки сегментов (N + N² + N³ кандидатов при глубине 3), складывая каждый промежуточный кандидат в список. Что сделать:

1. Заменить полный перебор на **послойный beam**: на глубине d хранить только top-B частичных цепочек по скору (после фикса P2), где `B = beam_factor × top_k`, новый CLI-параметр `--superpath-beam-factor` (default 5). Послойно: расширить все цепочки глубины d top-сегментами, отобрать top-B, перейти к d+1. Кандидаты всех глубин по-прежнему попадают в общий пул для финального top-k (как сейчас префиксные цепочки), но пул на каждой глубине ограничен B.
2. Жёсткий глобальный предохранитель: `--superpath-max-candidates` (default 100_000) — при достижении лимита генерация останавливается, в строку отчёта пишется флаг `superpath_truncated: true`.
3. Валидация: `--segment-min-length < 2` → ValueError в `main` (сейчас `max(1, …)` допускает 1, что даёт глубину перебора 12).
4. Согласовать дефолты: `segment_top_k=250` недостижим при пуле `top_starts × paths_per_start = 100`. Либо снизить default `--segment-top-k` до 100, либо в `_generate_superpath_segments` печатать warning, когда `segment_top_k > len(raw_paths)`; выбрать первое (снизить до 100) и отразить в README.
5. Отфильтровать сегменты с `vertex_delta <= 0` перед склейкой (новый параметр `--superpath-min-segment-delta`, default 1): они раздувают пространство и не могут улучшить суперпуть по скору после P2. Число отброшенных писать в строку отчёта как `segments_filtered_nonpositive`.

Тесты: (a) 250 плотно связанных сегментов длины 4 — `_build_superpath_candidates` завершается быстрее 5 секунд и возвращает ≤ top_k кандидатов (использовать `time.monotonic` с щедрым порогом, чтобы тест не флапал на медленных CI); (b) при превышении `superpath_max_candidates` усечение происходит и флаг выставлен; (c) `--segment-min-length 1` отклоняется.

## 3. P2 — убрать смешение единиц в скоре склейки

Сейчас `score = Σ vertex_delta + Σ edge_weight`, где `vertex_delta` — измеренные байты на TU (десятки–сотни), а `edge_weight` — вес ребра order-графа, в delta-режиме это сумма function-level дельт (тысячи). Glue-вес доминирует, и top-k фактически ранжируется графом, а не замерами — это инвертирует замысел эвристики.

Что сделать:

1. `SuperPathCandidate.score = Σ vertex_delta` сегментов (только измеренные байты). Поле `edge_score` сохранить как есть, но использовать его **только как тай-брейк** в `_superpath_rank_key`: ключ становится `(score, vertex_delta, edge_score, -len(passes), tuple(reversed(passes)))` — формально структура ключа не меняется, меняется лишь наполнение `score` (теперь score == vertex_delta; оставить оба поля для совместимости отчёта).
2. Переписать тест `test_superpath_candidates_combine_segment_delta_and_edge_weight`: на тех же данных ожидать `candidates[0].score == 15` (10 + 5), `edge_score == 20` как тай-брейк. Добавить тест, где сегмент с маленькой измеренной дельтой, но огромным glue-ребром (например, 10000) НЕ обгоняет пару сегментов с большими дельтами — это регрессионный тест на доминирование единиц.

## 4. P3 — штраф за пересечение сегментов и diversity при отборе на замер

Сегменты из `cycle_breaking_top_start_paths` — суффиксные варианты одних и тех же путей; склейки вида A + A′ двойным счётом выигрывают рейтинг, а реальная оценка показывает no-op. Что сделать:

1. При расширении цепочки сегментом B считать `overlap = |multiset(passes(B)) ∩ multiset(passes(цепочки))|`; если `overlap > --superpath-max-overlap` (default 1) — расширение отбрасывается. Учёт через `collections.Counter`.
2. Diversity на этапе отбора сегментов для замера: в `_generate_superpath_segments` после ранжирования применять жадный фильтр — сегмент берётся, только если его Jaccard-похожесть по множеству pass-ов с каждым уже взятым ≤ `--segment-max-jaccard` (default 0.75); добирать до `segment_top_k` или пока пул не исчерпан. Это сокращает бюджет замера на почти-дубликаты.

Тесты: (a) при двух сегментах с пересечением в 3 pass-а и `max_overlap=1` склейка не создаётся; (b) жадный diversity-фильтр отбрасывает суффиксный почти-дубликат и пропускает непохожий сегмент.

## 5. P4 — эксплуатация уже оплаченного кэша

Замер сегментов кладёт их префиксы в prefix cache, поэтому оценка суперпути A + B стоит только `len(B)` реальных запусков. При `--top-k 10` это почти не используется. Что сделать:

1. Новый параметр `--superpath-eval-top-k` (default 0 = использовать `--top-k`, для обратной совместимости). В nightly-скрипте для superpath-режима выставить его в 300 через env `SUPERPATH_EVAL_TOP_K`.
2. В строку отчёта добавить `segment_eval_cost` — число cache-miss, потраченных на фазу замера сегментов (зафиксировать `len(prefix_cache)` до и после фазы сегментов), и `superpath_eval_cost` — miss-ы фазы суперпутей. Это нужно для честного сравнения бюджета с `random_walk_top1000` в дипломе.

Тест: на мокнутых замерах с общими префиксами `segment_eval_cost + superpath_eval_cost + 1 == len(prefix_cache)` (плюс корень), и оценка суперпути из двух уже замеренных сегментов добавляет ровно `len(B)` новых ключей.

## 6. Мелочи (один коммит)

1. Удалить мёртвое поле `SuperSegmentCandidate.graph_score` (нигде не читается) — либо начать использовать его как последний тай-брейк в `_superpath_rank_key`; выбрать удаление.
2. Ветка `cycle_breaking_superpath_topk` в `generate_topk_paths` недостижима из `build_report` и при прямом вызове молча вернула бы голые сегменты — заменить тело ветки на `raise ValueError("use evaluate_superpath_for_benchmark for superpath heuristic")`.
3. Сегменты с `tail_failure`: вместо полного отбрасывания использовать их валидный best-prefix как сегмент, если его длина ≥ `segment_min_length` (vertex_delta пересчитать от `best_size`). Счётчик `segment_failures` сохранить, добавить `segments_recovered_from_tail`.

## 8. Что НЕ делать

- Не менять генерацию сегментов cycle-breaking-ом по существу (кроме diversity-фильтра из P3) и не трогать другие эвристики.
- Не менять семантику `vertex_delta` (он по-прежнему считается от baseline по `final_size` сегмента — это сознательный выбор для склейки).
- Не добавлять зависимости и многопроцессность.
- Не «улучшать по пути» prefix cache, `_selected_key` и формат summary сверх описанного.
