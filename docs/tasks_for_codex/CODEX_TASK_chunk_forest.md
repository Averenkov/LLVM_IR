# Задание для AI-агента (Codex): эвристика Chunk-Forest (chunked prefix-forest selection)

## 1. Контекст и идея

Лучшая текущая TU-эвристика — `random_walk_top1000` (~7.5% weighted best по `.text`). Она выигрывает объёмом слепых кандидатов. Chunk-Forest атакует четыре её слабости одновременно:

1. **Чанки** — взвешенные частые подпоследовательности pass-ов, добытые из per-function результатов CEM, восстанавливают порядок высшего порядка, который pairwise-граф теряет (идея MiCOMP/POSET-RL: поиск по под-последовательностям достигает ~90% выигрыша при ничтожном исследовании пространства).
2. **Повторы pass-ов** возникают естественно (чанки могут пересекаться по pass-ам) — пространство ближе к реальным пайплайнам LLVM.
3. **Префиксный лес**: бюджет оценки — это cache-miss в prefix cache, а не «число путей»; отбирая 500 путей с явной максимизацией общих префиксов, мы проверяем в 2–3 раза больше разнообразных хвостов за тот же реальный бюджет.
4. **Две волны по 250**: после реальной оценки первой волны ценности чанков пересчитываются по измеренным на TU маргиналам, и вторая волна корректирует перенос «функция → TU» — то, чего не делает ни одна текущая эвристика.

Бюджет: 500 путей на benchmark, сравнение с `random_walk_top1000` вести по `real_evals` (cache-miss), не по числу путей.

Общие правила прежние: регрессионные тесты на каждый блок, существующие тесты зелёные, ключи отчётов только добавляются, без новых зависимостей, LLVM в тестах не вызывается (моки замеров как в тестах superpath). Урок из фиксов superpath обязателен к учёту: НИКОГДА не складывать function-level веса (тысячи байт) с измеренными TU-байтами (десятки) в одном скоре без нормировки — см. раздел 6.3.

## 2. Структура кода

- `src/llvm_ir/heuristics/translation_unit/chunk_forest.py` — генератор: майнинг чанков, граф чанков, пул блужданий, субмодулярный отбор. Чистые функции, детерминизм по seed, ноль вызовов LLVM.
- `src/llvm_ir/stages/translation_unit/evaluate_chunk_forest.py` — evaluator с двухволновой логикой, по образцу `evaluate_superpath_for_benchmark`: переиспользует `evaluate_candidate_with_prefix_cache`/`evaluate_prefix`, `write_translation_unit_bitcodes`, baseline/Oz-замеры, `summarize_evaluations`, промежуточную запись отчёта. Entry point `llvm-ir-eval-tu-chunk-forest`.
- Вход: `--comparison <comparison.json>` (per-function результаты function search: имя функции, `best_passes`, `best_delta`) — группировка по benchmark-ам через `benchmark_id_from_function_name`; `--bitcode-dir` с whole-TU `.bc`. Order-граф benchmark-а строить внутри из тех же последовательностей (через `PassOrderGraph.add_sequence`, delta-режим) — он нужен только для `node_priority` одиночных pass-ов.

CLI:

```
--paths 500  --waves 2
--pool-size 100000  --walk-seed 7
--ngram-max 4  --closure-theta 0.8  --min-support 2  --top-chunks 30  --macro-top 3
--max-length 12        # длина пути в pass-ах
--lambda-cache 0.0     # вес штрафа за новые узлы леса; 0 = авто (см. 5.3)
--gamma-diversity 0.5  # затухание ценности повторно покрытого чанка
--max-real-evals-per-benchmark 0   # 0 = без лимита
[--measure-instructions] [--site-data ...] [--limit N] [--overwrite-bitcode] [--top-k 500]
```

## 3. Блок A — майнинг чанков (`mine_chunks`)

Вход: список `(best_passes, best_delta)` функций benchmark-а, `best_delta > 0` (остальные исключаются — как delta-режим графа).

1. **n-граммы**: все смежные подцепочки длины 2..`ngram_max`. Вес = сумма Δ функций, содержащих n-грамму; каждая функция считается ОДИН раз независимо от числа вхождений (support-семантика). Параллельно считать support (число функций).
2. **Замыкание**: для каждого ядра в порядке убывания веса расширять на один pass влево/вправо, пока лучшее расширение сохраняет ≥ `closure_theta` веса текущей цепочки; зафиксировать результат. Дедуп: одинаковые замкнутые цепочки схлопываются с максимальным весом ядра.
3. **Фильтр**: оставить замкнутые чанки с `support >= min_support`, взять top `top_chunks` по весу.
4. **Макро-чанки**: целые `best_passes` top-`macro_top` функций по Δ — отдельным сортом, без требований support.
5. **Одиночки**: top pass-ов по `node_priority` графа (из `path_scoring.py`) как чанки длины 1 — столько, чтобы суммарный инвентарь был ≥ 10 (для крошечных benchmark-ов).
6. **Fallback маленьких benchmark-ов** (урок superpath): если функций < `min_support` или майнинг пуст — инвентарь состоит из макро-чанков и одиночек; пул и отбор работают как обычно. Пустой инвентарь возможен только при пустом comparison для benchmark-а.

Выход: `Chunk(passes: tuple[str, ...], weight: float, kind: "mined"|"macro"|"single", support: int)`.

Тест-якорь (обязателен, числа проверены вручную): функции `encode Δ=1200 [sroa, instcombine, simplifycfg, gvn, dse, adce]`, `decode Δ=800 [sroa, instcombine, simplifycfg, gvn, licm, instcombine]`, `init Δ=300 [mem2reg, instcombine, simplifycfg, dse]`, `main Δ=0 [...]` (исключается). Ядро `(instcombine, simplifycfg)` имеет w=2300; замыкание при θ=0.8 даёт чанк `(sroa, instcombine, simplifycfg, gvn)` с w=2000 и support=2 (расширение на dse даёт 1200 = 60% < θ — стоп). Дополнительные тесты: анти-монотонность (расширение никогда не тяжелее ядра); n-грамма с support=1 не проходит min_support=2, но последовательность целиком доступна как макро-чанк; повтор pass-а внутри функции не удваивает вес (support-семантика).

## 4. Блок B — граф чанков и пул кандидатов

1. **Вхождения**: для каждой функции найти все вхождения каждого чанка (по позициям). **Рёбра**: для пары чанков (A, B) вес = сумма Δ функций, где вхождение B начинается после конца вхождения A с зазором ≤ 2 pass-а; функция считается один раз на пару. **Старты**: вес чанка как стартового = сумма Δ функций, где его вхождение начинается на позициях 0–1.
2. **Блуждания**: `pool_size` блужданий `random.Random(walk_seed)`: стартовый чанк по start-весам (взвешенный выбор), далее переходы по рёбрам графа чанков (взвешенный выбор; тупик = конец пути). Путь = конкатенация pass-ов чанков, обрезка по `max_length`. Повторное использование одного чанка в пути запрещено; повторы ОТДЕЛЬНЫХ pass-ов между разными чанками легальны. С каждым путём хранить его чанковую декомпозицию (нужна волне 2).
3. Дедуп пула по tuple pass-ов. Тесты: детерминизм по seed; декомпозиция корректна; обрезка по длине не ломает декомпозицию (обрезанный хвостовой чанк помечается partial и в credit assignment не участвует).

## 5. Блок C — субмодулярный жадный отбор 500

1. Скор пути до отбора: `path_value = Σ value(chunk)` по декомпозиции, где `value` — вес чанка из майнинга (волна 1) или измеренный (волна 2, см. 6.3).
2. Жадный отбор с диверсификацией: ведём счётчик `picked[chunk]`; marginal gain пути = `Σ value(chunk) × gamma_diversity^picked[chunk] − λ × new_nodes(path)`, где `new_nodes` — число префиксов пути, отсутствующих в префиксном trie уже отобранных путей (= будущие cache-miss). После выбора пути инкрементировать picked для его чанков и пополнить trie. Тай-брейк — лексикографически по пути.
3. **Калибровка λ** при `--lambda-cache 0`: λ = медиана `value(chunk)` по инвентарю / средняя длина чанка — чтобы штраф за узел был соизмерим с ценностью pass-а; зафиксировать формулу в docstring. Запрещено подбирать λ так, чтобы function-level веса напрямую сравнивались с TU-байтами где-либо ещё.
4. Остановка: набрано `paths/waves` путей ИЛИ суммарный прогноз miss-ов (размер trie) достиг `max-real-evals-per-benchmark/waves` (при ненулевом лимите).

Тесты: при λ > 0 из двух путей равной ценности выбирается делящий префикс с уже отобранным; при gamma < 1 второй путь из тех же чанков проигрывает пути с новыми чанками; жадный отбор детерминирован.

## 6. Блок D — двухволновая оценка

1. **Волна 1**: отобрать `paths/waves` путей (Блок C на mined-весах), оценить через prefix cache (best-prefix-семантика, как у всех evaluator-ов). Зафиксировать `wave1_real_evals` (прирост `len(prefix_cache)`).
2. **Credit assignment**: для каждого оценённого пути по его декомпозиции и записям prefix cache вычислить маргинал каждого не-partial чанка: `size(префикс до чанка) − size(префикс включая чанк)` (байты TU; чанки после первой ошибки в пути пропускаются). Для каждого чанка с ≥ 2 наблюдениями — `measured_value = среднее маргиналов` (может быть отрицательным).
3. **Перенормировка немеренных чанков** (КРИТИЧНО, урок superpath): чанки без измерений получают `value = mined_weight × scale`, где `scale = mean(measured_value по чанкам с измерениями, клип снизу 0) / mean(mined_weight тех же чанков)`; при пустом числителе scale = 0 (немеренные чанки не считаются ценными). Прямое сложение mined-весов с измеренными байтами без scale — ошибка.
4. **Волна 2**: пересчитать `path_value` пула на обновлённых value (отрицательные measured_value легальны и топят пути с вредными чанками), исключить уже оценённые пути, отобрать и оценить вторые `paths/waves`. При `--waves 1` блок D вырождается в одну волну (для абляции в дипломе).
5. Выбранная строка benchmark-а — лучший best_delta по ВСЕМ оценённым путям обеих волн (стандартный `_selected_key`).

Тесты (моки): чанк с большим mined-весом, но измеренным маргиналом ≤ 0 в волне 1, не доминирует отбор волны 2 (сконструировать пул, где без переоценки он бы выбрался); маргиналы считаются по границам чанков корректно (таблица размеров по префиксам); `--waves 1` эквивалентен однократному отбору 500.

## 7. Отчёт

Совместим с TU-eval отчётами: `selected_rows` (heuristic = `chunk_forest`), `candidate_rows`, `summary` через `summarize_evaluations` (+ instruction-summary при флаге), `prefix_cache_counts`, `config`. Дополнительно в строку benchmark-а: `chunks_mined`, `chunks_macro`, `chunks_single`, `pool_unique_paths`, `wave1_real_evals`, `wave2_real_evals`, `chunks_remeasured` (число чанков с measured_value), `rescoring_scale` (значение scale), `top_chunks` (top-5 чанков по итоговой value — passes и value, для главы диплома).

## 8. Интеграция и эксперименты

1. Nightly: блок за `RUN_CHUNK_FOREST=${RUN_CHUNK_FOREST:-0}`, параметры через env (`CF_PATHS`, `CF_POOL`, `CF_WAVES`, `CF_MAX_EVALS`), выход в `runs/<RUN_ID>/<algorithm>/translation_unit_chunk_forest/`.
2. README: раздел Chunk-Forest — алгоритм в 5 предложениях, параметры, и предписанная матрица сравнения: `chunk_forest (500, 2 волны)` vs `chunk_forest (500, 1 волна)` vs `random_walk_top500` vs `random_walk_top1000`, все с отчётом `real_evals` — сравнение по бюджету, не по числу путей.

## 9. Критерии приёмки

1. Полный тест-сьют зелёный; новые тесты падают на HEAD до реализации (для тестов генератора — тривиально, модуля нет).
2. Тест-якорь майнинга из раздела 3 проходит с точными числами (w=2300 → чанк w=2000, support=2).
3. Генератор на benchmark-е из 1 функции выдаёт непустой пул (fallback), evaluator возвращает строку без `error`.
4. Два запуска evaluator-а на моках с одинаковыми параметрами дают идентичный отчёт.
5. Коммиты: Блок A, Блок B, Блок C, Блок D + отчёт, интеграция — отдельно; сообщения на английском (`feat: add chunk mining for chunk-forest heuristic` и т.п.).

## 10. Что НЕ делать

- Не вызывать LLVM в генераторе и тестах; реальные замеры — только в evaluator-е через существующую инфраструктуру prefix cache.
- Не складывать mined-веса (function-level байты) с измеренными TU-байтами без scale из 6.3 — нигде.
- Не менять существующие эвристики, prefix cache, `_selected_key`, формат summary.
- Не добавлять зависимости (PrefixSpan не нужен — n-граммы и замыкание пишутся вручную); не использовать многопроцессность.
- Не превышать ~600 строк в каждом из двух новых модулей; если не помещается — упрощать, а не дробить на пакет.
