# Задание для AI-агента (Codex): superpath на маленьких benchmark-ах — best-prefix сегменты и ступенчатая деградация

## 1. Контекст

После предыдущих фиксов эвристика `cycle_breaking_superpath_topk` (`src/llvm_ir/stages/translation_unit/evaluate_topk_paths.py`) даёт нулевой результат на 5 из 30 benchmark-ов не из-за падений LLVM, а из-за собственных фильтров:

- `npb-v0_122` — граф из 1 pass-а, `npb-v0_3` — из 3, `mibench-v1_lame-newmdct-1` — 2 pass-а и 1 ребро: сегменты длины 4..6 невозможны, пул пуст, строка `no superpath candidates`. При этом random_walk на этих же benchmark-ах находит короткие пути с delta +270 / +226 / +221.
- `opencv-v0_442` — 12 сегментов, у всех неположительный final delta, хотя у одного best prefix даёт +8; `opencv-v0_50` — 21 сегмент, все с delta ≤ 0. Фильтр `--superpath-min-segment-delta 1` выкидывает всё, потому что вес сегмента считается по `final_size`, а не по `best_size`.

Цель: superpath не должен проигрывать тривиальным коротким кандидатам ни на одном benchmark-е. Принцип — graceful degradation: на больших графах поведение не меняется, на маленьких эвристика деградирует до перебора коротких путей.

ВАЖНО: пункт «Не менять семантику vertex_delta (final_size — сознательный выбор)» из предыдущего задания НАСТОЯЩИМ ОТМЕНЯЕТСЯ — P1 ниже меняет её сознательно и объясняет, почему это корректно.

Общие правила прежние: регрессионный тест на каждый пункт (падает до фикса), существующие тесты зелёные, ключи отчёта только добавляются, без новых зависимостей.

## 2. P1 — сегмент = лучший измеренный префикс сырого пути

Сейчас в `evaluate_superpath_for_benchmark` сегмент берётся целиком: `passes = tuple(segment_path)`, `vertex_delta = baseline_size - final_size`. Если хвост сегмента портит размер, хороший префикс теряется.

Что сделать:

1. После замера сырого пути через `evaluate_candidate_with_prefix_cache` строить сегмент из лучшего префикса: если `result["best_prefix_len"] >= 1` — `passes = tuple(result["best_passes"])`, `vertex_delta = baseline_size - int(result["best_size"])`; иначе (ни один префикс не улучшил) — сегмент с `vertex_delta <= 0`, который пойдёт под фильтр/предохранитель из P3.
2. Семантика склейки остаётся корректной: в суперпути применяется именно усечённая последовательность, и её измеренная дельта — это дельта того, что реально будет применено. Рёбра склейки (`outgoing`) считать от последнего pass-а УСЕЧЁННОГО сегмента — это происходит автоматически, если усечение выполнено до `_build_superpath_candidates`, проверить и закрепить тестом.
3. Объединить с уже существующим восстановлением из `tail_failure` (`segments_recovered_from_tail`): теперь оба случая (хвост упал / хвост ухудшил) идут через один код «взять best prefix». Счётчики в строке отчёта: `segments_truncated_to_best_prefix` (хвост ухудшил или сравнялся, префикс короче полного пути) и существующий `segments_recovered_from_tail` (был error). Если best prefix совпадает с полным путём — счётчики не инкрементировать.
4. Дедупликация: после усечения разные сырые пути могут схлопнуться в одинаковые `passes` — дедупить по tuple, оставляя один экземпляр (дельты у одинаковых passes одинаковы по построению кэша).
5. Фильтр `--superpath-min-segment-delta` применять ПОСЛЕ усечения.

Тест: сырой путь длины 5, у которого размер падает на шагах 1–2 и растёт на 3–5 (мокнутые замеры) → сегмент состоит из 2 pass-ов с положительной дельтой, glue-рёбра считаются от 2-го pass-а, счётчик `segments_truncated_to_best_prefix == 1`. Сценарий `opencv-v0_442`: из 12 сегментов с отрицательным final, один с best prefix +8 — он выживает и попадает в суперпути.

## 3. P2 — ступенчатая деградация длины сегментов на маленьких графах

Что сделать:

1. В `_generate_superpath_segments` ввести ступени: сначала фильтр длины `[segment_min_length .. segment_max_length]`; если пул пуст — `[2 .. segment_max_length]`; если снова пуст — `[1 .. segment_max_length]`. Использованную ступень писать в строки отчёта как `segment_length_floor` (значение фактического нижнего порога). Валидация `--segment-min-length >= 2` из предыдущего задания остаётся для пользовательского ввода; ступени — внутренний fallback, на CLI-валидацию не влияют.
2. Для крошечных графов перебор вместо cycle-breaking: если `len(graph.nodes) <= --tiny-graph-threshold` (default 4), генерировать ВСЕ простые пути длины 1..min(len(nodes), segment_max_length) по рёбрам графа (плюс одиночные ноды как пути длины 1) — их единицы, это дешевле и полнее, чем cycle-breaking. Пометить в строке `tiny_graph_mode: true`.
3. `cycle_breaking_top_start_paths` на графе из 1 ноды без рёбер должен корректно вернуть путь из одной ноды или пустоту — проверить и при необходимости обойти на уровне tiny-режима (не править сам cycle-breaking).

Тест: граф из 1 ноды → один сегмент-кандидат из 1 pass-а, оценивается, при положительной мокнутой дельте `best_delta > 0` в выбранной строке (сценарий `npb-v0_122` / `sroa` +270). Граф из 3 нод и 2 рёбер → перебраны все простые пути, лучший трёхшаговый найден (сценарий `npb-v0_3`).

## 4. P3 — гарантия непустых кандидатов

Что сделать:

1. Если после усечения (P1), ступеней (P2) и дельта-фильтра пул сегментов пуст, но измеренные сырые пути были — взять top-3 сегмента по `vertex_delta` БЕЗ дельта-фильтра (даже нулевые/отрицательные) и продолжить. В строку отчёта: `segment_delta_filter_bypassed: true`. Логика: кандидат с дельтой 0 безвреден (best-prefix-семантика финальной оценки всё равно вернёт неотрицательный best_delta), а строка `no superpath candidates` с нулём — это гарантированный проигрыш.
2. Строка `no superpath candidates` остаётся возможной только когда граф пуст (нет нод) или все сырые пути упали с `full_failure`. Отразить это условие в коде явно и в README.
3. `summarize_evaluations`/`add_failure_summary` не менять — улучшение увидим по падению `full_failures` и росту `weighted_best_percent`.

Тест: сценарий `opencv-v0_50` — все сегменты с дельтой ≤ 0, фильтр обойдён, лучший кандидат имеет `best_delta >= 0` (не ошибка), флаг bypass выставлен.

## 5. Мелочи

1. `--superpath-min-segment-delta`: уточнить help-текст — фильтр применяется к best-prefix дельте сегмента.
2. В README, раздел superpath: абзац про поведение на маленьких графах (ступени, tiny-режим, bypass) и таблица новых полей строки отчёта (`segment_length_floor`, `tiny_graph_mode`, `segments_truncated_to_best_prefix`, `segment_delta_filter_bypassed`).
3. Прогон с дефолтами на мокнутых данных: убедиться, что на «большом» графе (10+ нод, сегменты 4..6 существуют, дельты положительные) ни одна из новых веток не активируется и результат идентичен поведению до этого задания (байт-в-байт по выбранным строкам) — это отдельный тест на отсутствие регрессии.

## 6. Критерии приёмки

1. `PYTHONPATH=src python3 -m unittest discover -s tests -v` зелёный; новые тесты падают на HEAD до фикса.
2. Пять синтетических сценариев из раздела 1 (моки по описанию: 1-нодовый граф, 2-нодовый, 3-нодовый, «префикс +8 / финал −13», «все дельты ≤ 0») дают `best_delta >= 0` и отсутствие `error` в выбранных строках; для первых трёх `best_delta > 0` при соответствующих мокнутых размерах.
3. Тест «большой граф — поведение не изменилось» проходит.
4. Коммиты: P1, P2, P3, мелочи — отдельно, сообщения на английском (`fix: build superpath segments from best measured prefix`, `feat: tiered segment-length fallback for tiny graphs`, `fix: guarantee non-empty superpath candidate pool`).

## 7. Что НЕ делать

- Не менять cycle-breaking, random_walk и другие эвристики; tiny-режим живёт целиком внутри superpath-кода.
- Не ослаблять CLI-валидацию `--segment-min-length >= 2` — ступени являются внутренним fallback-ом.
- Не трогать beam-ограничения и нормировку скора из предыдущего задания.
- Не включать сегменты с отрицательной дельтой в склейку, кроме bypass-ветки P3 (там они допустимы только как одиночные кандидаты и для склейки между собой в пределах top-3).
